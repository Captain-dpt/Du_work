Autoware 包结构与 AiLabCar Lite 映射

2. AiLabCar Lite 的包级裁剪原则

Core消息定义、CMake、Utils、Lanelet2 基础能力属于大量包的公共依赖，原则上不直接手工删除。
Universe主要算法区。Perception 与 Planning 内部必须做白名单化，是实际裁剪收益最大的目录。
Launcher完整 autoware_launch 不作为最终比赛入口；建立 ailabcar_launch 只组合需要的节点。
Sensor不要为了“完整兼容”编译全部传感器驱动；控制器只保留 AiLabCar 当前真实硬件相关包。
External不能按目录整删。通过 --packages-up-to ailabcar_runtime 让依赖闭包决定真正需要的第三方包。
Dev ToolsSimulator、Evaluator、RViz/Visualization 可留开发机，但从比赛 Runtime 与启动链中移除。

裁剪完成后的源码模块化架构

该结构是 Minimal Stable Autoware 经过逐批裁剪、编译与功能回归后进入源码重构阶段的最终目标形态。 源码以 Autoware 保留下来的功能为基础重新按 AiLabCar 功能域组织：一个统一的 config 配置中心 + 各功能模块独立目录 + Bringup/Runtime 独立管理。 目标是让工程人员进入仓库后可以直接定位“参数在哪里、感知在哪里、定位在哪里、地图在哪里、规划在哪里、控制在哪里、CAN 在哪里、安全在哪里”。
Config：全系统统一配置中心 Core Domains：Sensing / Perception / Localization / Mapping / Planning / Control / Vehicle / System Infrastructure：Common / Interfaces / Bringup / Runtime Support：Drivers / Third Party / Tools / Scripts / Docs

模块裁剪清单

逐模块列出关键包名、决策和理由，可以直接当作 workspace 裁剪时的对照表。
层级 关键包 决策 理由
感知输入 Sensing pointcloud_preprocessor，LiDAR / camera driver，GNSS / IMU driver 保留 与建图/规划方式无关，直接复用现有驱动与点云预处理链路；也是 YOLO + LiDAR 感知链的输入基础。
定位 Localization ndt_scan_matcher，ekf_localizer，pose / twist estimator 替换 用实时建图 / 轻量定位 / GNSS-IMU 状态估计替代 NDT 对点云地图的强依赖；ekf_localizer 可保留，但输入源改成适合 AiLabCar 的定位来源。
地图 Map map_loader（pointcloud map + Lanelet2） 替换 / 精简 没有预制主车道语义地图时，退化为实时局部地图 / 简化 Lanelet2；如果赛事允许，也可以离线生成一份轻量先验地图。
感知-检测 tensorrt_yolo*，lidar detection / clustering，roi_cluster_fusion 保留 你当前已采用 YOLO + LiDAR 作为主要感知思路，这一层与默认 Autoware 检测链兼容度高，可以直接复用或做局部适配。
感知-跟踪 multi_object_tracker 保留 多目标跟踪算法本身不强依赖完整 Lanelet2 语义地图，对比赛场景仍然有直接价值。
感知-预测 map_based_prediction 替换 默认实现通常依赖 Lanelet2 拓扑与城市道路语义；在无复杂道路语义时，建议替换成运动学外推或轻量多假设预测。
规划-任务 mission_planner 替换 比赛更适合目标点 / 局部路径驱动，而不是面向城市车道网络的全局 route 规划。
规划-行为 behavior_path_planner，behavior_velocity_planner 大幅精简 其中大量模块（红绿灯、停止线、路口、人行横道等）属于法规场景，是裁剪量最大的部分；建议只保留赛道必需的轻量行为层。
规划-运动 obstacle_avoidance_planner，motion_velocity_smoother，trajectory tools 保留算法 / 换输入 核心运动规划与速度平滑算法仍可复用，但输入参考路径与障碍表达需改为 AiLabCar 的局部地图和规划接口。
控制 Control autoware_trajectory_follower_node，autoware_mpc_lateral_controller / autoware_pid_longitudinal_controller，autoware_vehicle_cmd_gate 保留 只要上游按轨迹接口输出，控制层基本可以不改；横纵向控制、命令仲裁与安全边界都应尽量保持稳定。
车辆接口 vehicle-specific driver，CAN interface 保留 与地图和规划语义几乎无关，按 AiLabCar 平台适配一次即可长期复用。
系统安全 System diagnostic_graph_aggregator，MRM handler，minimal system monitor 保留（精简） 建议保留最小诊断与最小风险机动功能。轻量化不等于删除安全边界。
仿真 Simulator planning_simulator，dummy_perception_publisher，simulator tools 移除 实车 Runtime 不需要。开发与验证阶段保留在 PC / 仿真工作区即可，不进入控制器部署包。
评估 Evaluator planning / control / perception_evaluator 移除 它们属于验证与分析工具，不是运行闭环依赖。
外部接口 autoware_adapi*，web_hmi，external API bridges 按需移除 若当前没有产品化 HMI 或外部业务接口需求，可以不进入 Lite Runtime；调试时只保留必要可视化接口。
V2X / Radar 对应专用感知包与融合包 移除 若 AiLabCar 当前没有相关硬件，直接裁掉整条链路，避免占用编译、磁盘与运行资源。
该表可直接作为 Autoware tag 1.71.2 → Autoware AiLabCar Lite 工作空间裁剪对照表。
注意：本表沿用早期未加前缀的包名（如 ndt_scan_matcher、behavior_path_planner、motion_velocity_smoother），与上方“Autoware 包结构与 AiLabCar Lite 映射”表中 autoware_* 前缀命名可能不是同一版本的确切包名（部分模块在近期 Autoware 版本中已合并/更名，例如 motion_velocity_smoother 与 motion_velocity_planner）。落地前务必以本地 tag 1.71.2 的 colcon list / ros2 pkg list 结果为准，统一成同一套包名再写入白名单。

Mapping → Autonomous 运行状态机

AiLabCar 与标准“已有 HD Map 后启动”的 Autoware 不同，因此必须明确首圈建图、地图冻结、验证、规划控制接管的状态转换。
BOOT→ SENSOR_READY→ MAPPING→ MAP_FREEZE→ MAP_VERIFY→ ROUTE_GENERATE→ AUTONOMOUS→ SAFE_STOP / MRM
MAPPING 完成条件
地图覆盖率、左右边界有效率、闭环/终点条件、地图几何合法性达到阈值。
MAP_FREEZE
冻结地图版本并停止结构性修改，生成唯一版本号与校验信息，避免规划过程中地图拓扑持续变化。
切换失败
Route 生成失败、TF 不一致、地图校验失败或定位不可用时，不允许进入 Autonomous，保持安全停车。

最小安全与故障处理链

轻量化不能把安全边界一起删除。至少保留传感器、定位、地图、规划、控制与 CAN 的时效性和健康状态监测。
Sensor HealthLiDAR / Camera / GNSS / IMU timeout、频率异常
Localization Health状态过期、跳变、TF 缺失
Map / Planning Healthmap_invalid、route fail、trajectory timeout / invalid
Control Healthcontroller timeout、command out-of-bound
Vehicle HealthCAN timeout、VCU fault、控制模式异常
Fault ManagerWARN → HOLD → SAFE STOP / MRM
关键要求：Planning 停止更新后，控制器不能无限复用最后一帧 trajectory/control command；必须设置 stale timeout 并通过 Command Gate 转入安全状态。
